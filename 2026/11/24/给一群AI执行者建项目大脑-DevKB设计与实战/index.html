一篇关于「多 AI 执行者协作的状态管理」的实践记录：真相源留在 markdown，数据库只做可丢弃的索引，看板只建议不越权。讲清 DevKB 的设计决策与两周实战里踩的坑。

脱敏状态：正文已用化名（项目A=在做的社区 App、某车厂项目、机器狗项目等），发布前按文末清单再过一遍

一、问题：AI 多了，记忆碎了

我现在同时养着几个 AI 编码执行者——Kimi、ZCode、Qoder、WorkBuddy，各有额度窗口和擅长面。白天我拍板，夜里它们自动领卡干活，早上我验收。听起来很美，但跑了一个月后，真正的瓶颈不是 AI 的编码能力，而是状态管理：

  • 每个项目的任务卡、执行日志、阻塞项、Bug 散落在各自的 markdown 文件里，格式还不完全一样
  • 我想知道”现在哪个执行者闲着、哪张卡能派、哪个项目在等外部”，得翻四五个目录
  • 跨项目问一句”上周修过类似的崩溃吗”，没有任何东西能回答
  • 更糟的是双写风险：如果看板自己存一份状态，项目 md 改了它不知道，两边很快各说各话

一句话：多个 AI 执行者缺一个共享大脑，而这个大脑不能变成第二个真相源。

二、核心决策：md 是真源，DB 只是索引

DevKB 的第一条设计原则，也是最重要的一条：

所有数据以项目内 markdown 为唯一事实源；数据库只是索引，随时可以删掉重建。

这个决策换来三个好处：

  1. AI 执行者零学习成本。它们本来就在读写项目 md（领卡改状态、写 PROGRESS、填执行结果），不需要学任何新 API。DevKB 对它们是透明的。
  2. 永不双写不一致。看板上想改任务状态？可以——但写入路径是 Web → 回写 md → 重跑同步器 → DB，md 永远先变。
  3. 索引可丢弃。db 文件坏了、schema 要改、换机器——重跑一次 sync 全回来。心理负担为零。

代价是查询前要先同步。我的处理是：不做加载时自动同步（避免页面一打开就静默写库），只在顶栏提示”索引落后源文件”，由人点”立即同步”。自动化场景则在每次写 md 后显式跑一次 sync；后来干脆把 sync 挂成了 launchd 定时任务（30 分钟一轮），人不用惦记。

三、同步器的四个硬功夫

sync.py 约 3100 行 Python 标准库代码（零第三方依赖），把”解析 markdown”这件脏活做出了几个值得说的细节。

3.1 内容指纹主键：幂等同步的根基

日志、Bug、测试记录没有天然 ID。用自增主键？每次同步都会重复插入。用行号？文件中间插一行全乱。

方案是内容指纹：

两个讲究：

  • 用 \x1f（单元分隔符）拼接字段，避免”字段内容恰好含分隔符”导致的指纹碰撞
  • 截断到 52 bit——不是随手截的：JavaScript 的 Number.MAX_SAFE_INTEGER 是 2^53-1，64 位整数传到前端会精度丢失，52 bit 刚好安全

效果：同一条日志同步一百遍也只有一行；内容改了指纹变，旧行删除新行插入，同步计数真实反映变化（+新增 ~变更 =未变 -删除，连续两轮应全为 0——这本身就是一条验收标准）。

3.2 源文件缺失守卫：别把”文件丢了”当成”数据删了”

早期版本有个隐患：某项目的日志文件被误删，sync 一跑，索引里几百条日志全被当成”已删除”清空。

现在的规则：首次同步时缺失的可选文件跳过；已索引过的项目若源文件缺失，整项目同步直接拒绝，保留旧索引：

宁可索引旧一点，不可把事故放大成数据丢失。类似的还有混合快照拒绝：采集期间源文件发生变化（mtime/哈希变了），整批拒绝重试，配合 savepoint 保证失败不留半批数据。

3.3 机器可读标注：零侵入的结构化

阻塞项、决策、指标这些”散落在正文里”的信息怎么入库？加 HTML 注释标注：

人读 markdown 渲染完全不受影响（注释不可见），机器用一条正则扫出七种标注（blocked/unblocked/decision/metric/risk/task/note）。还有个容易漏的细节：约定/模板类文档里的语法示例不是真实标注，扫描时按文件名排除（DOC_EXCLUDE = ("约定", "模板", "README")）——否则规范文档里教别人怎么写标注，自己先被入库了一堆假数据。

3.4 数据源契约：吃下格式完全不同的项目

第二个项目接入时问题来了：它是正规车厂项目，没有 .ai-tasks/ 任务卡体系，日志就是 git commit，任务写在 task_plan_*.md 里。

硬编码 if-else 能解决，但第三个项目呢？于是做了契约层：每个项目根放一份 .devkb/sources.json，声明自己的数据源路径和格式：

缺失时回落内置默认（老项目零改动）。git log 源特殊标记为 git:log，不参与源文件缺失守卫（commit 历史不会”丢文件”）。效果：车厂项目索引内现有 723 条日志（717 条来自 git）+ 10 张任务卡（其中 2 张来自 task_plan），和任务卡体系的项目在同一个看板里聚合。

四、Web 面板：只建议，不自动

面板是单页原生 HTML/JS + 标准库 http.server，12 个视图。两个视图体现”人机边界”的设计哲学：

健康度卡：每个项目一张——近 7 天日志活跃度、卡源分布（可派/待定/进行中/受阻/完成）、等外部项、P0 未完成需求、未闭环 Bug、开放风险。每行带口径 tooltip（”活跃度=近 7 天日志条数”这种定义直接可见，不用猜）。

分配建议：可派卡 × 空闲执行者 × 近 30 天历史吞吐 → 推荐排序。注意措辞——只建议，不自动派卡。派卡是有后果的动作（烧额度、占设备），最终决定权留给人。这条边界在我的自动化体系里是铁律：AI 可以建议、可以执行已拍板的卡，但不能自己决定派新卡。

写操作的安全层也值得提：所有 POST 要 CSRF token + 同源校验；回写 md 前做哈希校验，外部并发改动返回 409；Bug 登记带 request_id 幂等。本地工具做到这个程度，是因为回写的是真源——写坏一个 md，污染的是所有 AI 执行者的输入。

五、实战：一天的流水线

说个真实的工作日（项目名已脱敏）：

白天：我拍板”某项功能删掉，相关权限不会开放”。总控 AI 做四件事：

  1. 更新阻塞台账 md（拍板记录+执行说明），打上 devkb:blocked 标注
  2. 写执行卡进 .ai-tasks/zcode/INBOX/，卡内写清文件锁、红线、验收标准
  3. 排查存量卡冲突——发现有张实测卡会测到即将删除的功能，重写为”删改后回归卡”并加依赖；两张静态扫描卡加依赖确保扫的是改后代码
  4. 跑 sync.py，DevKB 里任务、阻塞、日志全部更新

23:00：派发脚本自动把 INBOX 待领卡发给执行者，启动语里写明依赖处理规则（前置卡未完成就跳过，全部过完回头重扫）。

次日 08:30：战报汇总每张卡结果。总控验收：读执行结果段、核对 git diff、跑编译门禁，通过的合入，DevKB 里卡状态变 ✅。

整条链路上，DevKB 不是”另一个要维护的系统”——它是 md 真源的自动投影。写 md 的动作就是喂数据的动作，零额外负担。

当前规模（2026-11-24 sync 实测）：8 个登记项目、1515 条操作日志、663 张任务卡、256 条测试记录、178 条需求、25 条 Bug、22 条阻塞、292 条知识条目；552 项测试守着（pytest 收集口径），端到端冒烟 10/10。

六、踩过的坑

  1. README 会过时，测试不会。第一次写本文时发现 README 还写着”66 项集成测试”，实际已 165 项。后来把统计块做成 sync 自动刷新（标记位替换），数字终于不用人肉维护——但新坑随之而来：pytest 收集数和 unittest 装载数两个口径会随执行环境翻转，README 数字一度 530↔491 来回跳。教训升级：自动生成的数字也要钉死口径。
  2. 免费模型表会失效。AI 兜底通道照搬旧项目的模型列表，白天实测发现前三个全部 404”不再免费”。教训写进了执行卡：外部依赖的可用性必须当天实测，禁照抄历史配置。
  3. 巡查器会”好心办坏事”。巡查 cron 把”执行者进程不在”当故障自动拉起，已明令停用的执行者被反复重启。修复：停用纪律写进 prompt 最高优先级，”进程不在=正常状态”。状态要有权威来源，不能让每个脚本自己猜——执行者状态后来也走了 md 真源（执行者状态.md，sync 解析入库）。
  4. 模板教的格式，解析器不认。写这篇 v2 时跑合规扫描抓到一个 fail：任务标注写成 task=Qxxx/status=done/commit=abc1234（斜杠分隔），而解析器按空格切 key=value——status 解析为空。追根溯源发现卡面模板里教执行者的就是斜杠写法，执行者照做没错，错在模板和解析器各说各话。修一处标注只能治标，模板源头才是病灶。教训：给 AI 的模板，每个示例都要先过一遍自己的解析器。
  5. 目录语义和状态行会打架。转派协议是”原卡 mv 到 transferred/ 留档 + 写去向行”，但 mv 不改内容，状态行残留”⬜待领”——索引把已转派的卡显示成可派，误导盘点。修复：解析时目录语义优先于过期状态行（transferred/ 里的卡一律归”已转移”），加回归测试锁死。教训：文件放哪本身就是状态，解析器不能只读文件里写了什么。

七、从看板到器官：四个”下一步”的落地

v1 结尾我列了四个方向：MCP 化、检索、全局聚合、事件通知。两周过去，前三个都落地了，第四个被更实在的东西替代。逐个说。

7.1 MCP server：AI 直接问，不用翻文件

mcp_server.py，237 行标准库，stdio 传输、换行分隔 JSON-RPC。六个工具：

工具 干什么
devkb_projects 列登记项目
devkb_tasks 查任务卡（项目/状态过滤）
devkb_blockers 查阻塞账
devkb_executors 执行者忙闲（md 真源同步产物）
devkb_query 只读 SELECT（拒 DML/DDL/多语句/PRAGMA attach）
devkb_sync 触发同步——唯一写路径，禁直写库

红线写死在实现里：对 DB 只读；不碰任何密钥文件；stdout 只输出协议 JSON，日志全走 stderr（混一行日志进 stdout，MCP 客户端就断连）。

7.2 CLI：总控脚本的一屏体检

MCP 给对话型 Agent 用，脚本型自动化（cron 巡查器、夜派脚本）要的是命令行。tools/devkb.py 九个子命令：status / projects / get / search / ingest / query / init / log / card。

最有用的两个：

  • **devkb status**：doctor + 三个探针 + 合规扫描聚合一屏，exit code 语义化（0=全绿 1=有告警 2=环境坏）。巡查 cron 的 prompt 从”跑五个脚本各自解析输出”变成”跑一条命令读一个 JSON”。
  • **devkb search**：FTS5 全文检索。中文检索有个绕不开的坑——SQLite 默认分词器不切中文。方案是 CJK 逐字分词：索引端把中文按字切开加空格，查询端同样处理，子串语义就出来了。实测搜”崩溃 修复”，跨项目命中开发日志、知识条目、迭代记录，bm25 排序，每条带源文件指针。v1 里”上周修过类似的崩溃吗没有任何东西能回答”——现在一条命令回答。

写侧命令带护栏：执行者白名单（exit 2 拒）、公司仓零写入（实测拒写留 WARN）、目录边界校验（不许动别的执行者的卡）。CLI 和 MCP 共用一个读侧实现（tools/read_model.py），SQL 白名单同源——两个门面一套内脏，不会各查各的。

7.3 派发前三查：把”派了才发现没额度”消灭在派之前

夜派脚本最大的浪费是派出去才发现执行者额度耗尽/在跑别的卡/卡被冻结。加了 GET /api/dispatch-check：一查额度窗口（含跨午夜区间）、二查在跑卡、三查冻结标记，返回 GO/NO-GO。夜派脚本先问再派，空转批次直接不启动。

7.4 装机：定时同步 + 看门狗 + 回归门禁

  • sync 定时化：launchd 每 30 分钟一轮，索引不再靠人记得刷
  • Hub 看门狗：每 15 分钟探活，连续两轮非 200 自动拉起
  • 回归门禁 gate.sh：五个核心文件任一改动 → 全套测试 + CLI 契约快照 + 双冒烟。挂成 pre-commit hook，但失败只警告不阻断——门禁是纪律不是枷锁，深夜批量提交不能被一个误报卡死
  • 契约快照：API 端点面、CLI 命令面各有一份 JSON 快照进版本库，测试逐项比对——执行者改代码时不小心动了接口面，测试直接红

事件通知没单独做：cron 战报 + status 聚合已经覆盖”阻塞解除/卡完成”的知晓需求，专门推一套通知系统属于过度设计。

八、下一步（如实评估）

  • 标注模板治理（✅ 写稿当天已落地）：六.4 的病灶按”容错在解析端”修掉了——解析器兼容斜杠分隔，历史标注不用追改，回归用例锁死两种写法
  • 空窗探针的夜间豁免（✅ 写稿当天已落地）：23:00–08:00 豁免窗上线，夜间休眠不再误报；白天空窗照报，正负控测试都在
  • RAG 检索：292 条知识条目比 v1 时的 15 条厚多了，历史执行结果段是天然语料——但 FTS5 关键词检索目前够用，向量检索等真出现”关键词搜不到”的实例再上
  • 开源：脚本和搭建手册先打磨稳再共享，到那天会更新这篇

写在最后

多 AI 协作的瓶颈不在编码能力，在状态管理。DevKB 的答案朴素但有效：真相源留在 AI 们本来就在读写的地方，索引层随时可重建，看板只建议不越权。从 2500 行长到 9400 行（同步器+面板+CLI+MCP），依然零第三方依赖，552 项测试守着。

这两周最大的体会：给 AI 建基础设施，每个”教 AI 怎么做”的模板、每条”AI 会怎么写”的假设，都要拿真实数据验一遍。本文 v2 的两个新坑（模板斜杠、目录语义）都是写稿时逐节核对抓出来的——写文章本身就是最好的一轮审计。

如果你也在同时用多个 AI 执行者干活，先别急着上平台——把 md 写规范，可能就已经赢了一半。
